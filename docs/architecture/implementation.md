# V0 architecture and requirement decisions

## TrainerStudio conventions

Implementation follows the frontend-architecture, frontend-testing and backend-v2-architecture skills reviewed in the TrainerStudio checkout, including their setup references and `backend/docs/architecture/v2.md`.

Three independent Vite workspaces separate presentation, citizen services and municipal administration (T2). `frontend/web` serves `/` with bilingual product information and links to both products; it has no API client or authentication bootstrap. `frontend/app` serves `/app/` with the citizen catalog, availability, reservations and history. `frontend/admin` serves `/admin/` with facility editing, calendars and indicators. Each has its own router, providers, styles, tests and build; there are no source imports between them. The citizen bundle contains no manager views or manager API calls. The backoffice requires a manager session before rendering operational controls. Both use the existing server-side audience permissions; frontends never grant permissions.

All dropdowns use Chakra `NativeSelect` with browser selection behavior. Build-time rules reject raw select elements and imports between frontends. Nginx routes each path to its own build and handles nested-route reloads. Development uses the website Vite proxy to the citizen server on 5174 and admin server on 5175. Cross-product links cause full document navigation. Locale is shared through `quenda.locale` on the same origin. The demo uses one HttpOnly API session cookie, so opening another audience's demo account replaces the active role; the citizen shell accepts only citizen sessions and the admin shell only manager sessions.

The frontend uses React Router route objects beside their pages. Page-owned subpages and components nest recursively under `components/`. Views render controller outputs; controllers own navigation and user input; TanStack Query owns server state; repositories alone know endpoint paths; the singleton fetch client handles transport. No barrel files are used. Search and sport filters live in the URL, locale in local browser preferences, identity in an HttpOnly cookie and server data in the query cache. Mutations invalidate reservations, notifications, availability and indicators. `scripts/check-architecture.mjs` checks component ownership, layer imports, cycles, endpoint count and guarded audiences.

Backend modules cover identity, municipalities, facilities, bookings and insights. Each v2 controller has one endpoint, explicit DTO mappings, strict request validation and exhaustive error handling. API problems use RFC 7807 with stable codes and Galician/Spanish messages. `Commands` and `Queries` resolve operations eagerly; only the command locator starts a transaction. Business failures are typed Results. Domain repository abstract classes double as injection tokens. `Clock`, `IdGenerator` and `Audit` are shared ports.

Public catalog and demo-session operations accept a municipality slug because no identity exists yet. Protected operations accept a principal whose tenant is derived from an opaque, server-stored session. The HTTP request cannot choose a protected tenant or user. Manager and citizen contracts use separate audience routes. Grant checks remain in the application operation, in addition to authentication at the edge. The facility-schedule port is owned by the booking consumer. Calendar expansion is a shared domain capability exported by the facilities module.

## PostgreSQL adaptation (T1, T2, T3, C2, R3)

The TrainerStudio adapter uses Mongoose. Quenda keeps its architectural rules and uses PostgreSQL instead: it is the context's recommended open database, and the `btree_gist` exclusion constraint expresses the reservation invariant directly. No TrainerStudio proprietary integrations or production data were copied.

Courts and sub-resources (M1, C1, C2). A facility owns one or more `resources` (courts, lanes, parts of a hall). Resources inherit sport, price, slot length, opening calendar and status from their facility; each one can be taken out of service on its own. A resource may group parts one level deep (a full court made of thirds). Bookings point at a resource, and every confirmed booking writes the **units** it occupies to `booking_units`: a simple resource occupies itself, a composite occupies all its parts and a part occupies only itself. The reservation constraint is `booking_units_no_overlap (tenant_id =, unit_id =, tstzrange(starts_at, ends_at, '[)') &&)`, so the full court excludes every third, each third excludes the full court, and two different thirds can be booked at the same time, even across independent API processes. Cancelling deletes the units and rescheduling rewrites them in the same transaction. The upgrade path gives every V0 facility one resource with the facility's own id, backfills `resource_id` and `booking_units` for existing reservations, and only then drops the old per-facility constraint. Occupancy indicators count open minutes per active unit, so a full-court booking weighs as many units as it blocks. Capacity (several people in one lane) is not modelled: every resource is exclusive. Adjacent slots are allowed. Composite foreign keys ensure the user, facility, resource and units belong to the reservation's municipality.

Open data (T3). The `open-data` module publishes each municipality's facility catalogue (schema.org JSON-LD, RFC 4180 CSV, RFC 7946 GeoJSON) and a DCAT-AP-ES catalogue under `/v2/public/open-data/`, with JSON Schema and Table Schema files served alongside. These responses override the global `Cache-Control: no-store` and helmet's `Cross-Origin-Resource-Policy` so other origins can reuse them; they read no cookies. Absolute URLs use `PUBLIC_URL` when set. Facilities have optional WGS 84 coordinates (`latitude`, `longitude`, both or neither), and municipalities have `data_license` and `dir3_code`. See [open data](open-data.md).

A command checks permissions, locks its user's row, locks the facility row, rechecks policy, and writes its booking, notification and audit event on one transaction connection. The user lock makes quota checks safe under concurrent requests. Facility locks serialize reservation changes with manager schedule edits. Expected exclusion failures map to `slot_taken`; error Results roll back all writes. AsyncLocalStorage transports the connection to repositories. Date values cross PostgreSQL as ISO strings and become Temporal objects in adapters; application code does not use JavaScript Date.

In-app notifications are transaction-local records. Email notices (C4) use a transactional outbox: `CreateBooking` and `UpdateBooking` call the shared `Outbox` port next to the in-app notice, so the message commits or rolls back with the reservation (a `slot_taken` leaves nothing queued). Each row carries a unique `dedupe_key` and never the address or the text. A separate worker process (`backend/dist/worker.js`, `npm run worker`, polling every `WORKER_INTERVAL_MS`) runs three commands. `ScheduleReminders` queues one reminder per reservation and start time, `reminder_hours` (default 24, per municipality) before it, only for reservations made before that window and for people who have an address and have not opted out; the key `reminder:{booking}:{start}` makes repeated or concurrent passes idempotent. `ClaimDeliveries` leases due rows with `FOR UPDATE SKIP LOCKED` and a two-minute lease, resolves recipient, language (`users.locale`, otherwise the municipality's), sender name and Reply-To, and closes rows nobody can receive. The worker then renders the gl/es template and sends through the `Mailer` port outside any transaction; `CompleteDelivery` records success or schedules a retry with exponential backoff (at most six attempts). Delivery is at-least-once: a crash between sending and recording repeats the message with the same `Message-ID`. One SMTP server serves the deployment (`SMTP_URL`, `MAIL_FROM`); each municipality signs with `mail_sender_name` and receives replies at `mail_reply_to`, falling back to its name and contact. Development and the demo use Mailpit (MIT) at http://127.0.0.1:8025. The `channel` column and the `Mailer` port leave room for Web Push (#35) and SMS without changing the commands. Notifica.gal is out of scope until a formal decision needs it.

## Demo identity and deployment (T4, R1)

Demo accounts are preconfigured per municipality. Opening a demo session is deliberately gated by `DEMO_MODE=true`. Tokens contain 256 random bits, are hashed in the database, expire after eight hours and are sent only as HttpOnly SameSite=Strict cookies. Production-mode cookies are Secure. Mutation requests must include a custom same-origin header; no cross-origin CORS allowance exists. Sessions are explicitly revoked at logout. Only fictitious display names are seeded.

Account lifecycle (T4). The data inventory, lawful basis, rights and retention rules are summarised in [data protection lifecycle](data-protection.md). Each municipality carries a `legal_version` for its privacy notice and a `retention_months` policy. Opening a citizen demo session requires the current `legalVersion`; the acceptance is stored in the append-only `consents` table and audited in the same transaction. Citizens hold the `account:own` grant, which allows `GET /v2/citizen/me`, a full JSON export at `GET /v2/citizen/me/export` (not subject to the history/notice limits) and `DELETE /v2/citizen/me`. Deletion anonymises in place because no foreign key cascades: future confirmed reservations are cancelled regardless of the notice period, the citizen's notices and sessions are removed, `display_name` is replaced and `deleted_at` is set; past reservations keep their row so aggregate indicators do not change. Deleted users are excluded from demo sign-in and, in `DEMO_MODE`, a fresh synthetic citizen is created when none remains. Audit events now record the actor role and optional details; `bookings.user_id` and `audit_events.actor_id` are nullable so a retention job can detach old rows. Each audit event records the actor role (`citizen`, `manager` or `system`) and, where useful, a `details` object: the booking interval for creations and cancellations, the before/after interval for reschedules, and the changed fields for facility edits (a changed opening calendar is flagged rather than copied). Managers hold the `audit:view` grant and read the log at `GET /v2/manager/audit`, filtered by period and action and limited to 500 events per request.

Retention (T4). `ApplyRetention` runs per municipality inside a `Commands` transaction with the injected `Clock`. Its cutoff is now minus `retention_months`, computed in the municipality's time zone. It sets `bookings.user_id` to NULL for reservations that ended before the cutoff, deletes older notices, nulls `actor_id` on older audit events (the action and details remain), purges expired sessions and finally removes consents and user rows of accounts deleted before the cutoff once nothing references them. It records a `retention.applied` system event with the counts. The exclusion constraint and the aggregate indicators do not read `user_id`, so they are unaffected. There is no in-process scheduler: run `npm run db:retention` in development or `node backend/dist/database/retention.js` in the `api` container, for example daily with `0 4 * * * docker compose exec -T api node backend/dist/database/retention.js`.

Attendance and no-shows (C3, M3). `bookings.status` adds `no_show`; "attended" is derived (a confirmed booking that has ended), so no job is needed. Managers hold `bookings:manage` and use `GET /v2/manager/bookings?date=` and `PATCH /v2/manager/bookings/:id`: a no-show can only be marked on the booking's local day once it has started, and only reverted afterwards. Each municipality configures a non-economic penalty (`no_show_limit`, default 3, 0 disables; `no_show_window_days`, 30; `no_show_block_days`, 7): reaching the limit inserts a `booking_blocks` row that makes `CreateBooking` fail with `booking_blocked`; reverting a no-show inside the window that led to the block lifts it. Every step notifies the person with a snapshot of their standing (`notifications.details`) and is audited. Municipal cancellations, one booking or a whole facility closure (`closureReason`, preceded by `GET /v2/manager/facilities/:id/impact`), record `cancelled_by='municipality'` and the reason, notify each person and audit each booking. Exports include blocks; retention deletes blocks that ended before the cutoff. Email delivery of these notices is left to the notification outbox.

Default listeners and Compose ports are loopback-only. The supplied demo does not implement production identity proof or regulatory compliance. Enabling an internet-facing service requires a separate deployment and identity implementation, HTTPS, operational hardening and the remaining T4 work listed in the README.

A global throttler guard limits requests per client IP, with a stricter limit on endpoints marked `@SensitiveEndpoint()` (sign-in); 429s are RFC 7807 problems. A scheduler entry point runs the `PurgeExpiredSessions` command at start-up and periodically, resolving it through `Commands` and using the injected `Clock`. TLS terminates in a front proxy (`deploy/Caddyfile`); nginx adds the SPA security headers and forwards `X-Forwarded-For`/`X-Forwarded-Proto`.

## Scope and rollout

The first usable slice covers catalog → calendar availability → reservation → reschedule/cancel → history/notices. Manager facility administration and basic aggregate indicators complete the demonstration path. Prices are informational; there is no payment processing. Schedule changes require future bookings to be resolved first; closing a facility with upcoming bookings requires a reason and cancels them on behalf of the municipality. Data remains durable across restarts.

A production roadmap should implement public identity (OIDC with Cl@ve/Chave365) and scheduled retention first (T4), then municipal configuration onboarding and notification delivery (R2, C4), followed by facility photos/subspaces, residency policies and operational reporting (M1–M3). QR/mobile are optional and follow mandatory requirements. Principal risks are identity-provider integration, municipal operating-policy differences and accessibility in real assistive-technology workflows.

## Validation (T5)

Vitest Browser Mode renders each frontend with real providers and routing; application tests retain real controllers and cache, replacing only HTTP with MSW/server-stubs. Website tests exercise the public entry and language switching. HTTP tests boot compiled Nest code and a real disposable PostgreSQL database. Calendar tests cover recurrence and DST edge cases. A separate Playwright smoke flow uses the real local stack, follows website → citizen app → admin → website links and verifies audience separation, reloads nested citizen and admin routes, changes native selects and checks mobile overflow. Twelve axe WCAG 2.0/2.1 AA scans cover the desktop/mobile website, desktop/mobile catalog, booking dialog, history, manager dashboard and facility editor. Automated checks are evidence, not certification or a substitute for assistive-technology/manual review.

## Local work integration (C3, C4, R1–R3, T3–T5)

Versioned migrations preserve the former unversioned `main` schema; see [migrations](migrations.md). [Municipal portability](data-portability.md) includes the current privacy, branding, attendance and email records. Personal [calendar subscriptions](calendars.md) follow both citizen and municipal changes and are revoked with account deletion. The browser smoke flow also downloads an ICS file, creates a subscription, checks its mobile layout, verifies revocation after deletion and downloads a municipal export.
